**Workload judged against:** PyTorch fine-tuning/inference of a ~200M-parameter vision–language model; checkpoints ~800 MB each, saved every 30 min; datasets a few GB; runs of a few hours; A100-class GPU wanted.

## ★ PRIORITY QUESTION — The 6-hour rule, quoted exactly

**Source:** Cluster Policies, https://nrp.ai/documentation/userdocs/start/policies/ — section heading "**Interactive use (6 hours max runtime)**" **[verified — NRP]**:

> "1. Pods do not stop on their own under normal conditions and won't recover if a node fails. Because of this, we assume any pod running without a controller is **interactive**, meaning it's used temporarily for development or debugging.
> 2. **Time limit:** such pods will be **destroyed in 6 hours** unless you request an exception for your namespace (in case you run JupyterHub or some other application controlling the pods for you).
> 3. **Resource limits:** interactive pods are limited to 2 GPUs, 32 GB RAM, and 16 CPU cores.
> 4. It is okay to run `sleep` in an interactive pod."

Corroborated in Using Nautilus, https://nrp.ai/documentation/userdocs/start/using-nautilus/ : the Pod/Job/Deployment table gives Pod "**Max Runtime: 6 hours**", "Max Resources: 2 GPUs, 32 GB RAM and 16 CPU cores"; Job "Runs to completion"; Deployment "2 weeks". And in ML/Jupyter pod, https://nrp.ai/documentation/userdocs/jupyter/jupyter-pod/ : a self-run Jupyter container "will be automatically destroyed in 6 hours."

### Answers to the five sub-questions

1. **Per-session or per-day? Per pod/session — it is NOT a daily cap.** The rule attaches to "any pod running without a controller." No per-day usage quota, daily GPU-hour budget, or cooldown is stated anywhere in the NRP documentation (**no daily limit documented**). Nothing in the docs forbids starting a new pod/server immediately after one is destroyed; the limit re-applies to the new pod. (Caveat: this is an inference from the rule's wording and the absence of any daily cap — the docs never say in so many words "you may restart immediately.")
2. **What happens at the limit? The whole pod is destroyed — the GPU is not detached.** The verb is "destroyed" (pod, with its container, processes, memory and GPU allocation). **Warning before it fires: NOT DOCUMENTED** — no warning, grace period, or notification for the 6-hour interactive destruction is stated anywhere. (Contrast: the separate 2-week Deployment purge does promise "3 notifications" — Policies, "Workloads purging.")
3. **Does the home volume survive? Yes for persistent volumes generally; the hosted-hub home specifically is described as "persistent."** Policies (Workloads purging): "Any data in persistent volumes will remain." The JupyterHub Service page calls the home a "**persistent** home folder." What is in RAM / in the container filesystem outside a mounted volume is lost with the pod. Note the 6-hour interactive rule should not even reach a hosted-hub server in the normal case — see (4).
4. **Is it GPU-specific? No. Are there separate idle timeouts for CPU vs GPU? The docs draw no CPU/GPU distinction.** The 6-hour rule applies to *any* controller-less pod, GPU or CPU. Crucially, it is aimed at bare pods, and the rule itself names the exception: pods controlled by an application — "**in case you run JupyterHub**" — are the exception case. Hosted-hub servers are KubeSpawner pods controlled by JupyterHub, so the operative limit for a *hosted hub server* is not this 6-hour destruction but **idle culling**: Deploy JupyterHub, https://nrp.ai/documentation/userdocs/jupyter/jupyterhub/ , requires every JupyterHub deployment to "cull idle servers" with `timeout` = "**Maximum idle time before culling (in seconds). Must be ≤ 21600 (6 hours)**", example `timeout: 3600` (1 hour), `every: 600`, and `maxAge: 0` ("Maximum age of servers regardless of activity (0 = no limit)"). That page governs people *deploying their own* hub; **the hosted hub's own configured `timeout`/`maxAge` values are NOT DOCUMENTED** on the JupyterHub Service page or anywhere else in the NRP docs. Two third-party/index sources put the hosted West hub's practical behaviour at ~1 hour after browser disconnect / ~1 hour of inactivity: UCR Research Computing, https://ucr-research-computing.github.io/kb/kb025-nautilus-jupyter-and-coder/ ("Your server shuts down 1 hour after your browser disconnects… Files in your home folder survive; whatever was running in memory does not") **[index/3P]**, and an NRP training site snippet (training.nrp-nautilus.io) saying idle servers are "culled about an hour after your browser disconnects" **[index]**. Treat "1 hour idle/disconnect" as likely but not NRP-documentation-verified.
5. **Does requesting more resources change the limit? No — if anything the opposite.** The time limit is flat; the resource caps (2 GPUs / 32 GB / 16 cores) are the *ceiling for interactive pods*, not a dial that buys time. No page states that larger requests extend (or shorten) any time limit. **NOT DOCUMENTED** any resource↔duration trade-off.

**Practical reading for this workload:** a few-hours run fits inside a single 6-hour window *if* it stays "active" — but an API-driven, browser-less run is exactly what idle culling is designed to reap, and the hosted hub's actual idle timeout is undocumented (possibly ~1 h). The documented safe route for multi-hour computation is a Kubernetes **Job** (no 6-hour cap, runs to completion — §7, Added Question B).

## Added questions A–D (Jobs are the long-run route)

### A. How a regular user gets kubectl access to their namespace
**Source:** Getting access, https://nrp.ai/documentation/userdocs/start/getting-started/ **[verified — NRP]**
1. Log in at nrp.ai via **CILogon** (select your institution; Microsoft/Google/GitHub fallbacks listed). Account is created on first login; AUP acceptance registers the account but gives no compute (Hierarchy page, https://nrp.ai/documentation/userdocs/start/hierarchy/ ).
2. **Get a namespace:** a student is added by their research supervisor; faculty / university staff / postdocs request their own via the form at https://get-started.nrp-nautilus.io (log in to nrp.ai first; name = group name, "lowercase letters, numbers, and dashes only"). Membership is checked at https://nrp.ai/namespaces (yours under "Mine"). A Project in the hierarchy **is** a Kubernetes namespace; the Group Administrator is the namespace `admin`. **NOT DOCUMENTED:** any automatic namespace naming derived from your university — the name is chosen on the request form / by your admin, it is not a formula.
3. **Install tools:** `kubectl`, plus the `kubelogin` plugin — "You **must** install the `kubelogin` plugin, or your kubeconfig file **will not work**" (installed as `kubectl-oidc_login`).
4. **Kubeconfig:** download the config file from **https://nrp.ai/config** and save it, extensionless, as `~/.kube/config` (e.g. `curl -o ~/.kube/config -fSL "https://nrp.ai/config"`). Context name is `nautilus` (`kubectl config use-context nautilus`); set your default namespace with `kubectl config set-context nautilus --namespace=<YOUR_NAMESPACE>`.
5. **First use:** any `kubectl` command opens a CILogon browser login. "By default the access token expires in half an hour and is automatically updated after that" (`kubectl oidc-login clean` forces a refresh). Verify with `kubectl get pods -n <YOUR_NAMESPACE>` — "No resources found" means access works.

### B. Specifying a Job: GPU type (A100), image, CPU/RAM, and volumes — do checkpoints survive?
**Sources:** Running Batch Jobs, https://nrp.ai/documentation/userdocs/running/jobs/ ; GPU Pods, https://nrp.ai/documentation/userdocs/running/gpu-pods/ ; Storage tutorial, https://nrp.ai/documentation/userdocs/tutorial/storage/ ; Priority Classes, https://nrp.ai/documentation/userdocs/running/priority-classes/ **[all verified — NRP]**
- **Shape:** `apiVersion: batch/v1`, `kind: Job`; per-container `image:` (the docs' example uses `gitlab-registry.nrp-nautilus.io/prp/jupyter-stack/prp` and clones code from GitLab in an init container); `restartPolicy: Never`; example `backoffLimit: 5` (retries on non-zero exit / node reboot — checkpoint-friendly). The Job's command **must end by itself**; `sleep infinity` in a Job gets the user **banned** (Policies).
- **CPU/RAM/GPU:** `resources.requests` and `resources.limits` with `cpu`, `memory`, and the GPU key. Docs' Job example: limits `memory: 6Gi, cpu: "6", nvidia.com/gpu: "1"` / requests `memory: 4Gi, cpu: "1", nvidia.com/gpu: "1"`. Policies require limits within **20%** of requests.
- **A100 specifically, two documented ways:** (i) request the special resource **`nvidia.com/a100: 1`** in *both* limits and requests (special-resource table also lists `nvidia.com/h100`, `/h200`, `/gh200`, `/a40`, `/rtxa6000`, `/rtx8000`, `/mig-small`); or (ii) request `nvidia.com/gpu` and pin the type with node affinity: key **`nvidia.com/gpu.product`**, `operator: In`, values such as `NVIDIA-A100-SXM4-80GB` (the memory table lists "NVIDIA A100 SXM4 | 80"). **Quota trap:** "A100 quota is zero by default" — without a reservation (requested at https://nrp.ai/reservations) an A100 Job will not schedule under the default priority; the documented bypass is `priorityClassName: opportunistic`, which bypasses GPU quota but means the pod "**can be preempted by any other pod in the cluster**, so checkpoint frequently or run it as a Job so the controller can restart it."
- **GPUs per Job:** "up to 8 per node if you're using jobs, and up to 2 for pods" (GPU Pods). Jobs have no documented per-Job GPU cap beyond node size.
- **Volumes / checkpoint survival:** create a PVC in *your* namespace (see C), then in the Job pod spec: `volumes: [{name: examplevol, persistentVolumeClaim: {claimName: test-vol}}]` and per-container `volumeMounts: [{name: examplevol, mountPath: /examplevol}]` (tutorial's exact field names). Data on a PVC survives pod/Job deletion: Policies — "Any data in persistent volumes will remain." So 30-minute checkpoints written to the PVC mount survive preemption, node failure (with `backoffLimit` restart) and Job completion.
- **⚠ The JupyterHub home volume does NOT bridge into your Jobs — NOT DOCUMENTED as mountable, and the docs point the other way.** The hosted hub runs in namespace **`jupyterlab`** (Support page, https://nrp.ai/documentation/userdocs/start/support/ ), and "PVCs are scoped to a particular namespace… not directly accessible or visible to other namespaces" (Storage tutorial). The documented pattern is: **create your own PVC in your own namespace and use it from your Jobs/pods**; treat hub-home and Job storage as two separate stores and sync via S3/Git (see §5).

### C. Storage classes and sizes for user-created volumes beyond the 5 GB hub home
**Sources:** Ceph FS/RBD, https://nrp.ai/documentation/userdocs/storage/ceph/ ; Storage tutorial (above) **[verified — NRP]**
- **Size is user-chosen, no cap documented:** a PVC requests its size in `spec.resources.requests.storage`; the official tutorial example requests `storage: 1Gi` (`rook-ceph-block`, `ReadWriteOnce`, "creating a 1GB volume"). **No maximum PVC size, per-namespace storage quota, or default size is stated anywhere in the NRP docs — NOT DOCUMENTED.** (Ask Nautilus Support before requesting anything very large; fair-use/resource policies apply generally.)
- **Classes (exact names):** CephFS `ReadWriteMany` — `rook-cephfs` (US West), `rook-cephfs-central`, `rook-cephfs-east`, `rook-cephfs-south-east`, `rook-cephfs-pacific`, plus local/restricted `rook-cephfs-haosu`, `-tide`, `-fullerton`, `-ucsd` (NVMe, purge-at-discretion policy). RBD block — **`rook-ceph-block` (*default*)**, `ReadWriteOnce`, US West, plus `rook-ceph-block-central/-east/-south-east/-pacific/-tide/-fullerton`. Guidance: block "provides fastest access… and **is preferred for all datasets not needing shared access from multiple pods**"; CephFS mounts the same volume from multiple pods in parallel. Rule from llms.txt/policies: **do not install conda/pip packages on CephFS**.
- **Other stores:** Ceph **S3** object storage (no size stated; §5) and ephemeral `emptyDir` scratch (**>50 Gi** written without requesting `ephemeral-storage` can get the pod evicted — Using Nautilus).

### D. Exact Authorization header for Hub API tokens — confirmed
**Source:** JupyterHub REST docs, https://jupyterhub.readthedocs.io/en/5.2.0/howto/rest.html and the server-API tutorial, https://jupyterhub.readthedocs.io/en/stable/tutorial/server-api.html **[JH]**
The scheme is the literal word **`token`**, not `Bearer`:
```http
Authorization: token <your-api-token>
```
Every official example uses it: `headers={"Authorization": f"token {token}"}`, `curl -X POST -H "Authorization: token <token>" …`. The same header + same token authenticates to the single-user server's API provided the token carries the `access:servers` scope (§3). Do not confuse this with NRP's *managed-LLM* endpoint (https://ellm.nrp-nautilus.io/v1), which *does* use `Authorization: Bearer <token>` — a different service and a different token.

## 1. The Service and Access
**Sources:** JupyterHub Service, https://nrp.ai/documentation/userdocs/jupyter/jupyterhub-service/ ; Using Nautilus; Getting access; Support **[verified — NRP]**
- **What it is:** "We provide a hosted JupyterHub service running in the NRP. Using the hosted JupyterHub which is convenient if you need to quickly run your workflow and do not want to learn Kubernetes." Listed as a **Stable** (supported) service in Deployed Services, https://nrp.ai/documentation/userdocs/start/resources/ . It runs in namespace **`jupyterlab`**.
- **URL / hostname pattern:** the hub is **https://jupyterhub-west.nrp-nautilus.io** (the only hosted hub URL the docs give; "west" matches the US-West region of its storage). The general NRP service pattern is `<name>.nrp-nautilus.io` (Coder: `coder.nrp-nautilus.io`, GitLab: `gitlab.nrp-nautilus.io`, S3: `s3-west.nrp-nautilus.io`, etc.). Per-user server URLs follow the standard JupyterHub pattern `{hub}/user/<username>/` (§3) **[JH]**.
- **Authentication:** "use your institutional credentials to login using **CILogon**" — you must (a) have an institution in CILogon and (b) **be a member of a namespace**: "You **do** need to be part of a namespace to use the NRP-hosted JupyterHub service" (Using Nautilus / llms summary). No separate hub password.
- **Creating an API token [JH]:** JupyterHub docs (NRP publishes no token instructions of its own — **NRP-specific token guidance NOT DOCUMENTED**): while logged in, open the token page via the `token` link in the top nav or at **`/hub/token`** (in JupyterHub 5.0 the page is `/hub/tokens` and accepts scopes as a space-separated list). Programmatically: `POST /hub/api/users/{username}/tokens` with JSON body fields `scopes` and `expires_in`, authenticated with an existing token.
- **Default token scopes [JH]:** Scopes, https://jupyterhub.readthedocs.io/en/5.2.0/rbac/scopes.html . The default token metascope is **`inherit`** — "the token to have the same permissions as the token's owner"; it is "still the default behavior for requesting a token if limited permissions are not specified." For a normal (non-admin) user, `inherit` resolves to the user metascope **`self`**, which expands to (for user `gerard`): `users!user=gerard`, `servers!user=gerard`, `tokens!user=gerard`, `access:servers!user=gerard` — i.e. read/manage *your own* model, activity, servers and tokens, and access your own servers via API/browser. Relevant named scopes: `servers` = "Start and stop user servers" (subscopes `read:servers`, `delete:servers`); `read:servers` = read server models (needed for status calls, §2); `access:servers` = talk to the server itself (§3). A token can never exceed its owner's permissions. **NOT DOCUMENTED:** which JupyterHub version the hosted hub runs, and whether NRP altered any default roles/scopes.

## 2. Hub API — Server Control
**Sources:** JupyterHub server-API tutorial and REST how-to (§D) **[JH]**; NRP publishes **no** Hub-API documentation of its own (**NOT DOCUMENTED in NRP docs** — everything here is upstream JupyterHub behaviour that the hosted hub inherits).
Auth on every call: `Authorization: token <token>` (§D). Base: `https://jupyterhub-west.nrp-nautilus.io`.
- **(a) Read user model / server status:** `GET /hub/api/users/:username` — required scope `read:servers`. Response contains a `servers` dict keyed by server name (default server key is `""`). Each server model has exact fields: `name`, `ready` (bool), `pending` (`null`, or `"spawn"`/`"stop"`), `url` (e.g. `/user/test-1/`), `user_options`, `progress_url` (e.g. `/hub/api/users/test-1/server/progress`), `last_activity`, `started`. Empty `servers: {}` = no server running.
- **(b) Start/spawn:** `POST /hub/api/users/:username/servers/[:servername]` — required scope `servers`. Responses: **201** = created and ready immediately; **202** = accepted, `pending: "spawn"` — poll the user model until `ready: true`, or stream `GET /hub/api/users/:user/servers/:servername/progress` (EventStream, `data: {"progress": 0-100, "message": …, "ready": true, "url": …}`).
- **(c) Stop:** `DELETE /hub/api/users/:user/servers/[:servername]` — required scope `servers`. Responses: **204** = fully stopped (gone from the model); **202** = `pending: "stop"` — no progress API for stopping; poll until the server disappears from `servers`.
- **Can the spawn POST carry the web form's choices? — Mechanism yes [JH]; exact NRP field names/values NO, NOT DOCUMENTED.** Upstream: "Setting `user_options` directly via the REST API… The body of a POST request to spawn a server may be a JSON dictionary, in which case the `user_options` field will be used to set `user_options` directly. When used this way, neither `options_form` nor `options_from_form` are involved… only `apply_user_options` is called" (Spawners, https://jupyterhub.readthedocs.io/en/latest/reference/spawners.html ; pre-6.0 the whole JSON body became `user_options`). What those options *mean* "will depend on the Spawner's configuration." For KubeSpawner, profiles are `profile_list` entries with `display_name`, `slug`, `default`, and `kubespawner_override` (which can set `image`, `cpu_limit`, `mem_limit`, `extra_resource_limits: {nvidia.com/gpu: …}`), selected via the `profile` user-option — but **NRP does not publish the hosted hub's profile list, profile slugs, form field names, or any `apply_user_options` hook**, and the hub's JupyterHub/KubeSpawner version is not stated. **Say it plainly: from the documentation alone you cannot construct a spawn request that reliably selects image, GPU type, GPU count, CPU, RAM or region on this hub. An API spawn with an empty body defaults to whatever the hub's default profile / last-used `user_options` give you (upstream KubeSpawner persists `user_options` in the hub DB and reuses them on later spawns if none are given) — which image/GPU that is on NRP's hub is NOT DOCUMENTED.** The one documented workaround is human-in-the-loop: spawn once through the web form with the desired choices, then drive that running server via the API (§3).
- **What the web form offers** (for comparison): the NRP service page says only "Choose the hardware specs to spawn your instance." A university guide to this exact hub lists the Server Options fields as **Region** (default: Any), **GPUs**, **Cores**, **RAM**, **GPU Type** (optional; "Leave as *Any* unless you need specific hardware"), and **Image** — CSUF Titan Supercomputing, https://csuf.screenstepslive.com/m/129011/l/1956146-step-by-step-how-to-get-started-with-jupyterhub **[index/3P, not NRP]**.

## 3. Server API — Running Code
**Sources:** JupyterHub REST how-to + server-API tutorial **[JH]**; Jupyter Server API spec, https://raw.githubusercontent.com/jupyter-server/jupyter_server/main/jupyter_server/services/api/api.yaml (search-indexed) **[JH/index]**
- **URL pattern:** `{hub_url}{server_url}` — i.e. take the server model's `url` field (`/user/:username/` for the default server, `/user/:username/:servername/` for named) and append the Jupyter Server API path: **`https://jupyterhub-west.nrp-nautilus.io/user/<username>/api/…`**.
- **Auth:** the *same* user token, same header `Authorization: token <token>`, works against the server API **if the token has the `access:servers` scope** — a default `inherit`/`self` token for the server's owner includes `access:servers!user=<you>` (§1). "The same API token can also authorize access to the Jupyter Notebook REST API provided by notebook servers managed by JupyterHub if it has the necessary `access:servers` scope."
- **Contents API (upload/download):** `GET /api/contents/{path}` (model or file content), `PUT /api/contents/{path}` ("Save or upload file"), `POST /api/contents/{path}` (create new file/dir), `PATCH` (rename), `DELETE`, plus `/api/contents/{path}/checkpoints` (POST create / GET list / restore). File bodies are JSON models with a `content` field (base64 for non-text formats) — workable for scripts/notebooks, clumsy for 800 MB checkpoints; prefer in-server downloads (§6) or S3 (§5) for bulk data.
- **Kernels API (execute code):** `GET /api/kernels`, `POST /api/kernels` (start; body can name the kernelspec), `GET /api/kernels/{kernel_id}`, `DELETE /api/kernels/{kernel_id}`, `POST /api/kernels/{kernel_id}/interrupt`, `POST …/restart`, `GET /api/kernelspecs`. Actual code execution runs over the **WebSocket** channel `WS /api/kernels/{kernel_id}/channels` (execute_request messages) — REST alone does not execute code; clients must implement the Jupyter messaging protocol over that socket (e.g. via `jupyter_client`/`websocket` libraries). Sessions API (`/api/sessions`) binds a notebook path to a kernel.
- **Terminals:** `GET /api/terminals`, `POST /api/terminals` (create), `GET/DELETE /api/terminals/{terminal_id}`; terminal I/O is likewise WebSocket-based. A terminal is the practical API route to shell commands (`curl`, `pip`, training scripts) inside the server.
- **NOT DOCUMENTED (NRP):** any NRP-specific statement that the hosted hub permits token access to servers, any rate/size limits on the Contents API, and whether named servers are enabled on this hub (`allow_named_servers` is an admin setting; its state here is not published).

## 4. Limits
**Sources:** Policies; Using Nautilus; Deploy JupyterHub; GPU Pods; Priority Classes **[verified — NRP]**
- **Session/server lifetime:** bare (controller-less) pods destroyed at **6 hours** (§★). Hosted-hub servers: idle-culled at an **undocumented** timeout that by admin rule must be ≤ **21600 s (6 h)** of *idle* time; the admin example is **3600 s** and third-party reports say ~1 h after browser disconnect for West **[index/3P]**. `maxAge` (absolute age cap) in the admin example is **0 = no limit**; the hosted hub's setting is **NOT DOCUMENTED**. **Daily usage limits: none documented anywhere.**
- **Enforcement:** automatic — a periodic process destroys interactive pods at 6 h; JupyterHub's cull service checks every `every: 600` s in the example and shuts down idle servers (culling servers, `users: false`, does not delete accounts). Deployments are purged at **2 weeks** after **3 notifications**, data in PVs remaining. Volumes **not accessed for 6 months can be purged without notification**. Resource misuse is policed via the portal **Violations** page; namespaces with consistently under-utilised requests "risk being banned"; a Job ending in `sleep` = ban.
- **Utilisation rule:** a user may not run **more than 4 pods** violating: **GPU utilisation > 40%** of requested GPUs, CPU within 20–200% of request, memory within 20–150% of request (pods requesting 1 CPU + 2 GB are exempt). Request **1 GPU** unless utilisation is near 100%; plans for **> 50 GPUs** must be presented in Nautilus Support first. **Do not submit > 400 Jobs at once** (Using Nautilus / coding-agents page); there is **no fair queue** — "If you submit 1000 jobs, you block all other users."
- **GPU inventory (GPU Pods page, which warns the table "is not up to date — it's better to use `kubectl get nodes -L nvidia.com/gpu.product`"):** memory table (GB): GTX 1070/1080, Quadro M4000 **8**; A100 MIG 2g.10gb **10**; GTX 1080 Ti, RTX 2080 Ti, TITAN Xp **12**; Tesla T4 **16**; **A10, RTX 3090, RTX 4090, TITAN RTX, RTX A5000, Quadro RTX 6000 — 24**; Tesla V100 SXM2 **32**; **A40, L40, RTX A6000, Quadro RTX 8000 — 48**; **A100 SXM4 — 80** (the only full A100 row in the table); **H200 NVL — 141**. **A100 variants:** the table does **not** split A100 40 GB vs 80 GB — it lists only "NVIDIA A100 SXM4 | 80" plus MIG slices (1g.10gb as special resource `nvidia.com/mig-small`; 2g.10gb at 10 GB in the table). A 40 GB A100 exists in the cluster's `gpu.product` labels (third-party guides list `NVIDIA-A100-SXM4-40GB` and `NVIDIA-A100-PCIE-40GB`) but **NRP's own GPU-types table does not document a 40 GB A100 row — treat 80 GB SXM4 as the documented A100, 40 GB as index-only**. Special-resource request keys: `nvidia.com/a100`, `/h100`, `/h200`, `/gh200`, `/a40`, `/rtxa6000`, `/rtx8000`, `/mig-small` (RTX PRO 6000 Blackwell `nvidia.com/rtx6000bw` "reserved… not generally available").
- **How many GPUs / type selection:** interactive pods ≤ **2 GPUs**; Jobs ≤ **8 per node**; Deployments **0** (no GPU allowed). Type selection in Jobs/pods is by special resource key or by `nvidia.com/gpu.product` node affinity (values are node labels, e.g. `NVIDIA-GeForce-GTX-1080-Ti` in the docs' worked example); region follows the node/storage region you schedule into — there is no cross-region GPU guarantee documented. On the hub form, GPU Type defaults to "Any" **[index/3P]**. **A100 quota = 0 by default**; reservation or `opportunistic` (preemptible) required (§B).

## 5. Storage
**Sources:** JupyterHub Service; Deploy JupyterHub; Ceph; Ceph S3; Moving Data; Purging; Policies **[verified — NRP]**
- **Persistent home `/home/jovyan`:** "Your persistent home folder **initially will be limited to 5GB. If you need more, you can request it to be extended.**" That is the whole statement: **to whom / how is NOT stated on the service page** (the platform's only documented support channel is Nautilus Support / Matrix — Support page; the scientific-images page likewise routes requests to "Nautilus Support"). **What happens if it fills: NOT DOCUMENTED** — no quota-exceeded behaviour, grace, or read-only state is described anywhere. Budget reality for this workload: 5 GB ≈ six 800 MB checkpoints with *nothing else* in home — datasets (a few GB) + checkpoints + pip installs will not fit; an extension or a separate PVC/S3 is mandatory, not optional. (For self-deployed hubs the template shows the mechanism: `storage.capacity: 5Gi`, `homeMountPath: /home/jovyan`, class `rook-ceph-block`, `ReadWriteOnce`, PVC name template `claim-{username}{servername}`.)
- **Shared/team storage:** only documented for *self-deployed* hubs (mount an extra PVC at `/home/shared`, needs `ReadWriteMany`/`ReadOnlyMany`). For the hosted hub, team sharing is via your own namespace PVCs (CephFS RWX, §C) and S3 buckets with bucket policies — **no shared folder inside the hosted hub is documented**.
- **Scratch/ephemeral:** container filesystem + `emptyDir` die with the pod; **>50 Gi** of scratch per container without requesting `ephemeral-storage` risks eviction.
- **Object storage (the bulk-data route):** Ceph S3, free, "not part of Amazon." Credentials from the portal (User → S3 Tokens; https://nrp.ai/s3token/). Outside endpoints `https://s3-west.nrp-nautilus.io` (also `-central`, `-east`, `-haosu`, `-tide`, `-ha`); inside-cluster endpoint `http://rook-ceph-rgw-nautiluss3.rook` (http, higher bandwidth). Known issue: AWS CLI multipart uploads **> ~80 MB** can fail — use rclone/s3cmd/boto3, or set `multipart_threshold = 1GB`, `multipart_chunksize = 256MB` (tested "with files larger than 1 GB") — directly relevant to 800 MB checkpoints. **No S3 size/quota is documented.**
- **Persistence rules:** storage is **not archival**; purge what you don't need; volumes untouched **6 months** may be purged without notice; the UCSD NVMe CephFS (`rook-cephfs-ucsd`) may be purged at admin discretion. Deleting a Coder workspace deletes its PVC; deleting a Job/pod does not delete PVC data.

## 6. Internet Egress
**Sources:** Moving Data; Special Use; Jobs; Ingress **[verified — NRP, by implication + one explicit exception]**
- **General egress works and is a documented workflow:** Moving Data instructs users to *pull data into a pod* from "a storage which can be accessed from outside (any cloud provider, a server, etc.)" using `wget`/`curl` (HTTP servers), `scp`, or `rclone`, and Jobs examples clone from GitLab and pull container images. Nothing in the docs names an egress allowlist, a required proxy, or blocked destinations for ordinary pods/servers. **Hugging Face, GitHub and PyPI are never named in the NRP docs — NOT DOCUMENTED either way**; by the documented pull-from-any-HTTP-server pattern they are expected to work, but this is inference, not a documented guarantee.
- **Documented exception:** "Some nodes in the cluster **don't have access to public Internet, and can only access educational network. They still can pull images from Docker Hub using a proxy.**" (Special Use) — you only land on those nodes if you deliberately tolerate `nautilus.io/science-dmz`, so a normal hub/Job pod is not on them, but node placement is the hub's choice, not yours.
- **Inbound is the restricted direction:** pods "are not accessible from outside"; inbound HTTP needs an Ingress (`*.nrp-nautilus.io`), non-HTTP TCP exposure requires asking Nautilus Support; cross-namespace traffic times out without a NetworkPolicy. **NOT DOCUMENTED:** any egress firewall, DNS filter, or bandwidth cap for hub servers specifically.

## 7. Long Jobs
**Sources:** Policies; Jobs; JupyterHub deploy/culling; UCR guide **[NRP + index/3P where marked]**
- **Browser closes:** the server is a cluster pod, not a browser process — closing a tab does not itself kill a running kernel/process. What kills it is **idle culling** (§★/§4): third-party reporting on this hub says shutdown follows ~1 h after browser *disconnect* **[index/3P]**, and JupyterHub's culler judges *server activity* (API/kernel activity counts; a purely API-driven client that keeps executing and polling may register as active — **whether API/kernel activity resets this hub's cull timer is NOT DOCUMENTED for the hosted hub**).
- **Server culled or stopped:** the pod is destroyed — kernels, terminals, background/`nohup` processes and all in-memory state die with it; `nohup` only detaches a process from a terminal, not from its pod, so **background processes are NOT expected to survive a cull/stop/restart** (no NRP page promises otherwise; the stateless-pod tutorial demonstrates files outside volumes vanishing on pod deletion). On restart you get a fresh pod with the **same `/home/jovyan` volume** — files, checkpoints and `pip install --user` packages saved there survive; running work does not resume.
- **Documented guidance for long/batch work — do not use the hub for it:** "We highly recommend using **Jobs** for any kind of development and computations in our cluster. This will ensure you never lose your work… Once your development is done, you are immediately ready to run large-scale stuff" (Jobs page). Jobs **run to completion** (no 6-h cap), retry via `backoffLimit`, log via `kubectl logs`, and mount PVCs for checkpoints (§B). The Jupyter-pod page says the same: the interactive Jupyter container "will be automatically destroyed in 6 hours. Use the examples for Jobs once you're done with interactive debugging and ready to run a bigger job."
- **Non-Jupyter route to the same cluster:** yes — full `kubectl` access to your namespace (§A), plus Armada batch scheduling (`armadactl`, Scheduling page) and Coder workspaces (up to **5 active workspaces**, 5 GB home, GPU templates — Coder page). These are the documented production routes; the hub is positioned as the prototyping front end.

## 8. Images
**Sources:** Scientific Images, https://nrp.ai/documentation/userdocs/running/sci-img/ ; Deploy JupyterHub; CSUF guide **[NRP + index/3P]**
- **The named image:** "**NRP Deep Learning & Data Science Full, PyTorch**" (also listed with a "(CUDA)" suffix in the CSUF guide) is, in NRP's own description, the **NRP image with additional libraries** — `gitlab-registry.nrp-nautilus.io/nrp/scientific-images/python` — "based on Docker Stack TensorFlow and PyTorch, with additional packages"; the installed-package list lives on its GitLab page (https://gitlab.nrp-nautilus.io/nrp/scientific-images/python). The CSUF guide summarises its contents as "PyTorch, CUDA, full data science stack" **[index/3P]**. **PyTorch version and CUDA version are NOT DOCUMENTED** — neither the Scientific Images page, the service page, nor any other NRP page states a version number for this image; the only versioned CUDA facts in the docs are node driver/runtime labels (check with `kubectl get nodes -L nvidia.com/cuda.runtime.major,…`) and example images elsewhere (`nvidia/cuda:12.4.1-…-ubuntu22.04`). Verify versions from inside a running server (`torch.__version__`, `torch.version.cuda`) — the docs cannot tell you in advance.
- **Image families on the hub:** Jupyter **Docker Stacks** (CUDA only in the TensorFlow and PyTorch variants) and **B-Data** (CUDA + ARM); plus a Desktop/Selkies image. Use the `base` Python environment as kernel; use `python`/`python3`, not `/usr/bin/python3`.
- **Custom/different libraries, three documented routes:** (1) ask for packages to be added to the NRP image — "We can add more libraries to this image by requesting in Nautilus Support"; (2) install into home (`pip install --user`, conda envs under `/home/jovyan/my-conda-envs/` with `nb_conda_kernels` + `.condarc` — persists across sessions, eats the 5 GB); **never pip/conda-install onto CephFS volumes**; (3) for your *own* pods/Jobs/hub, build any image you like (extend `jupyter/minimal-notebook` or a scientific image, add `jupyterhub`+`notebook` packages for hub use) and push to `gitlab-registry.nrp-nautilus.io`, Docker Hub or Quay — Jobs/pods take any `image:` string. **NOT DOCUMENTED:** any way to add a custom image to the *hosted* hub's spawn list yourself — that list is admin-controlled.

## Bottom line

**Can this hub, driven purely through its API with a user token, support the workload? Only for prototyping — not as the production path, and not fully API-selectable.** The token mechanics are solid and fully documented upstream (`Authorization: token …`; status/spawn/stop endpoints; server Contents/Kernels/Terminals APIs under `/user/<username>/api/…` with the `access:servers` scope), and a few-hours run with 30-minute checkpointing to `/home/jovyan` is physically plausible. But three facts break the pure-API plan: (1) **spawn options are a black box** — NRP publishes no profile slugs or `user_options` field names for image/GPU type/count/CPU/RAM/region, so an API spawn gets an undocumented default (you cannot even guarantee an A100, or any GPU, without a human first spawning via the web form); (2) **time limits are hostile to headless runs** — bare pods are destroyed at 6 h, hub servers are idle-culled at an undocumented timeout (admin ceiling 6 h, third-party reports ~1 h after disconnect), with no documented warning, and everything running dies while only home-volume files survive; (3) **storage and GPU quota are undersized/gated by default** — 5 GB home cannot hold a few-GB dataset plus a rolling set of 800 MB checkpoints, and A100 quota is zero without a reservation (or preemptible `opportunistic` access). **Top three operational risks:** ① silent idle-cull/6-hour destruction mid-run losing all work since the last checkpoint; ② API spawn landing on the wrong image/GPU (or no GPU) because spawn options are undocumented; ③ home volume filling mid-run (quota behaviour undocumented) — compounded by A100 preemption if accessed opportunistically. **Recommended shape, per the docs themselves:** prototype on the hub, then run the real fine-tuning as a Kubernetes **Job** (§A/B) with `nvidia.com/a100`, a self-sized Ceph PVC for checkpoints, and `backoffLimit ≥ 1`.
